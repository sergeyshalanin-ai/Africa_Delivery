Сценарий 1: пик нагрузки в день запуска
Стимул (событие): Одновременный рост трафика до 5 000 активных пользователей и до 500 RPS на критические API.
Источник: Покупатели, пришедшие из рекламных кампаний
Среда: Первые 72 часа после запуска; активна рекламная кампания; нормальный режим работы.
Артефакт: Africa Delivery Platform: Catalog, Orders, Payments, Delivery.
Ответ: Платформа масштабирует вычислительные ресурсы, обрабатывает запросы, сохраняет работоспособность критического пути и не допускает потери заказов.
Мера ответа: 99,9% успешных запросов критического пути; p95 API каталога ≤ 500 мс; p95 создания заказа ≤ 800 мс; 0 потерянных заказов.

Сценарий 2: сбой платёжного провайдера
Стимул (событие): платежный сервис возвращает ошибки, не отвечает или задерживает вебхук о статусе платежа.
Источник: Flutterwave, Paystack или M-Pesa.
Среда: Пиковая нагрузка в день запуска; один из платёжных провайдеров недоступен или деградировал.
Артефакт: Payments Service и интеграционный адаптер PSP.
Ответ: Система фиксирует заказ в статусе «ожидает оплаты», выполняет retry с экспоненциальной задержкой, не создаёт дубликат платежа, показывает покупателю понятное сообщение и при необходимости переключает трафик на доступный PSP.
Мера ответа: 100% заказов сохраняются; 0 дублирующих платежей; webhook обрабатывается в течение 5 минут; время обнаружения сбоя ≤ 5 минут.

Сценарий 3: сбой базы данных
Стимул (событие):  PostgreSQL становится недоступным.
Источник: Инфраструктурный сбой: отказ БД, сетевая проблема или повреждение инстанса.
Среда: Нормальная эксплуатация или час пик; managed PostgreSQL.
Артефакт: Database layer, Orders, Catalog, Payments.
Ответ: Система обнаруживает отказ, переключается на read replica или восстанавливает primary, сохраняет целостность данных и возобновляет обработку заказов.
Мера ответа: RTO ≤ 4 часа; RPO ≤ 15 минут; успешное восстановление из бэкапа подтверждается disaster recovery drill не реже одного раза в квартал.

Сценарий 4: попытка несанкционированного доступа
Стимул (событие): Попытка подбора пароля, несанкционированного доступа к админ-панели, эксплуатации уязвимости API или кражи токена.
Источник: Внешний злоумышленник или автоматизированный бот.
Среда: Публичный интернет; нормальная эксплуатация; возможна распределённая атака.
Артефакт: API Gateway, Authentication, Admin Portal, Payments API.
Ответ: Система ограничивает число попыток, требует MFA для административного доступа, блокирует подозрительный трафик, записывает событие в audit log и уведомляет on-call при критическом шаблоне атаки.
Мера ответа: 100% административных доступов с MFA; 0 секретов вне secret manager; 100% критичных событий в audit log; 0 критических уязвимостей до запуска; блокировка подозрительного IP в течение 1 минуты.

Сценарий 5: изменение требований к локализации данных
Стимул (событие): Требование изменить правила хранения, обработки или трансграничной передачи персональных данных нигерийских пользователей.
Источник: Внешний юрист, регулятор Нигерии или местный консультант.
Среда: Период до запуска в ЮАР или после получения финального юридического заключения.
Артефакт: Data storage, Orders, Payments, Analytics, интеграции с внешними системами.
Ответ: Архитектор анализирует влияние, определяет затронутые потоки данных, обновляет модель хранения и интеграции, готовит ADR и план миграции без изменения всей бизнес-логики.
Мера ответа: Оценка влияния — не более 5 рабочих дней; реализация изоляции перс данных в Нигерии — не более 4 недель; 0 нигерийских пользователей за пределами страны без юридически подтверждённого основания.
